## ✅ 設計方針の確定

### ユーザーヒアリング結果

|質問                |回答                      |
|------------------|------------------------|
|セキュリティ vs 品質      |**「外に出ない」が最優先**         |
|ローカルモデルの日本語品質許容ライン|**正確で伝わること必須。文章の美しさは不要**|

### 確定した設計方針

> **「データが外に出ない」をデフォルトにする。クラウドAPIはオプション。**

- マーケティングメッセージ：**「社内資料は、一切外に出ません。」**（完全ローカルモード時、初回モデルダウンロード完了後の通常利用において常時成立する）
- デフォルト動作：完全ローカル。**初回起動時のモデルダウンロード完了後は、インターネット接続不要で動作する**
- クラウドAPI：上級者向けオプション。品質向上が目的。**ユーザーが明示的に有効化した場合のみ、チャンクテキストが外部送信される**

> **「完全ローカルモード＝外部通信ゼロ」は、初回モデルダウンロード完了後の通常利用時に成立する。初回起動時のみインターネット接続が必要。** この点をオンボーディング時にユーザーへ明示する。

## 📖 プロジェクト共通定義

|用語                 |定義                                                               |
|-------------------|-----------------------------------------------------------------|
|**インデックス作成**       |フォルダ内ファイルをテキスト抽出→チャンク分割→Embedding→ベクトルDB格納する一連の処理。モデルの書き換えは一切行わない|
|**チャンク**           |テキストを意味の塊に細切れにした単位。デフォルト1200文字（≒600トークン）、オーバーラップ500文字 |
|**Embedding（埋め込み）**|テキストの意味を多次元数値ベクトルに変換したもの。本製品では常にローカル実行                           |
|**ベクトルDB**         |Embeddingを保存・検索するローカルDB。ChromaDB（HNSWlib基盤）                      |
|**RAG**            |質問に対し①ベクトルDBから関連チャンクを検索→②チャンク＋質問をLLMに渡して回答生成する本製品の根幹技術           |
|**ローカルLLM**        |PC上で動作する回答生成モデル。Ollama HTTP API経由で推論。完全ローカルモードで使用。外部通信ゼロ         |
|**クラウドLLM**        |Gemini / Claude / GPT等の外部API。オプションモードで使用。チャンクが外部送信される            |
|**完全ローカルモード**      |Embedding・LLM両方をPC内で処理。外部通信ゼロ。デフォルト設定                            |
|**クラウドAPIモード**     |LLMのみ外部API使用。回答品質が向上する。ユーザーが明示的に選択する上級者向けオプション                   |
|**BYOK方式**         |Bring Your Own Key。クラウドAPIモード時のみ必要。APIキーはユーザー管理                  |
|**差分インデックス**       |SHA-256ハッシュで変更検知。新規・変更・削除ファイルのみ再処理                               |
|**エビデンス**          |回答の根拠として提示する出典情報（ファイル名・フォルダパス・ページ/スライド番号）。表示形式：「フォルダパス ＋ ファイル名」で統一（フルパス）|
|**スキップログ**         |処理できなかったファイルの一覧。保存場所: `~/.monoshiri/logs/skip_log.txt`。記録内容: ファイル名・エラー理由・タイムスタンプ（ファイル内容は含まない）|
|**キャッシュ**          |ローカル保存されたベクトルDB＋ファイルハッシュ管理ファイルの総称                                |
|**一時ファイル**         |インデックス作成中に生成される中間ファイル。処理完了・エラー・キャンセル時に必ず削除する                      |
|**チェックポイント**       |チャンク処理の進捗を記録するファイル。中断・再開を可能にする                                  |

### 技術アーキテクチャ原則

1. **モデルゼロ書き換え原則**：ファインチューニング・再学習は行わない
1. **ローカルファースト原則**：デフォルトは外部通信ゼロ。クラウドは明示的オプト・インのみ
1. **Embeddingは常にローカル原則**：モードに関わらずEmbeddingは常にPC内処理
1. **透明性原則**：すべての回答にエビデンスを付与
1. **ポータブル原則**：ZIP解凍→exe起動のみ。依存ライブラリ・モデルは全同梱
1. **BYOK原則**：クラウドAPIキーはユーザー管理。モノシリ社はAPI費用を負担しない
1. **最小権限原則**：アプリは管理者権限不要。ユーザーが選択したフォルダのみにアクセス
1. **正直さ優先原則（v4.0追加）**：回答に自信がない場合は「見つかりませんでした」と正直に返す。ハルシネーション（嘘の回答）を出すよりも、無回答を選択する（ADR-002）

## 動作モード設計

### モードA：完全ローカルモード（デフォルト）

```
ユーザーの操作：フォルダ選択 → 質問するだけ
外部通信：ゼロ（インターネット接続不要）
APIキー：不要

処理フロー：
  質問入力 → ベクトルDB検索（ChromaDB・類似度閾値0.80固定） → ローカルLLM（Ollama・デフォルト: Qwen2.5-7B） → 回答＋エビデンス表示
  ※ LLM回答が不十分と判定された場合は末尾に外部資料調査の案内を自動付加
```

### モードB：クラウドAPIモード（オプション・Phase 2）

```
ユーザーの操作：設定画面でAPIキーを入力して有効化
外部通信：チャンクテキストのみ（Embeddingは引き続きローカル）
APIキー：必要（BYOK方式）
対応LLM：Gemini Flash / Claude Haiku / GPT-5 Nano
```

**UI上の明示：「⚠️ このモードでは、資料の一部テキストが外部サーバーに送信されます。」**

### モード比較

|項目    |完全ローカル（デフォルト）|クラウドAPI（Phase 2） |
|------|-------------|---------------|
|外部通信  |**ゼロ**       |チャンクのみ         |
|APIキー |**不要**       |必要             |
|回答品質  |正確・伝わる（文章は簡潔）|自然な日本語         |
|処理速度  |PCスペック依存     |高速             |
|コスト   |**無料**       |API従量課金（ユーザー負担）|
|対象ユーザー|**全員（デフォルト）**|品質向上を望む上級者     |

## ローカルLLMのモデル管理設計

### 基本方針

> **「初期モデルを同梱しつつ、ユーザーが自由にモデルを追加・切り替えできる」設計にする。**

- モデルの進化が速いため、特定モデルへの依存を避ける
- GGUFフォーマット対応モデルであれば何でも動作（Ollama経由）
- 現場PCのスペックに合わせてモデルを選べる柔軟性を持たせる

### LLM推論バックエンド（v4.0変更: ADR-001）

> **llama-cpp-python から Ollama HTTP API に移行。**

|項目        |内容                                    |
|----------|---------------------------------------|
|バックエンド    |**Ollama HTTP API**（ローカル動作・MIT License）|
|通信先       |`http://localhost:11434`（localhost限定）  |
|GPU管理     |Ollama側で自動検出・自動オフロード                   |
|モデル形式     |GGUF（Modelfile経由でOllamaに登録）           |
|ストリーミング   |NDJSON形式のストリーミングAPI                    |
|プリウォーム    |起動時に選択モデルをVRAM/RAMに事前ロード              |

**移行理由（ADR-001）:**
1. GPU設定の自動化（非エンジニアユーザーがGPU設定を意識しない）
2. チャットテンプレート内蔵（ChatML等の自前管理が不要）
3. モデルプリウォーム対応（初回質問の遅延を解消）
4. ストリーミング推論の標準対応

### プリセットモデル（v4.0更新: 5種）

### チャットテンプレート

全プリセットモデルは**ChatML形式**を使用。Ollamaに登録する際のModelfileでテンプレートを指定。

```
<|im_start|>system\n{システムプロンプト}<|im_end|>
<|im_start|>user\n{ユーザーメッセージ}<|im_end|>
<|im_start|>assistant\n
```

### モデル追加の仕組み

```
方法A：HuggingFaceからダウンロード
  → モデルIDを入力 → 量子化選択 → ダウンロード進捗バー → 完了後すぐ選択可能
  ※ セキュリティ：HTTPS強制、GGUFマジックナンバー検証

方法B：ローカルGGUFファイルを直接追加
  → PC上のGGUFファイルをパス指定 → GGUFフォーマット検証後、即時追加・選択可能
```

### モデル登録フロー（Ollama）

```
1. GGUFファイルの絶対パスを取得
2. Modelfile を生成:
   FROM /path/to/model.gguf
   PARAMETER num_gpu 99          # 全層GPUオフロード
   PARAMETER num_ctx 2048        # コンテキスト長
   PARAMETER temperature 0       # 決定論的出力（RAG精度優先）
3. ollama create [ollama_name] -f [modelfile_path] で登録
4. プリウォーム（最小リクエストでVRAM/RAMにロード）
```

### 動作要件（モデルサイズ別）

|スペック |14Bモデル     |7〜9Bモデル    |3Bモデル      |
|-----|-----------|-----------|-----------|
|RAM  |32GB以上     |16GB以上      |**8GB以上**  |
|ストレージ|空き15GB以上   |空き10GB以上   |**空き5GB以上**|
|CPU  |Core i5相当以上|Core i5相当以上|Core i3相当以上|
|GPU  |VRAM 8GB以上推奨|なくても動作（あれば高速化）|なくても動作|

### 起動時のモデル自動判定

```
起動時：
  PCのRAMを自動検出
    → 32GB以上：14Bモデルも選択可能（7Bがデフォルト）
    → 16GB以上：7Bモデルを推奨・デフォルト
    → 8GB以上：3Bモデルを推奨・デフォルト
    → 8GB未満：警告を表示（動作は試みる）
```

- 製造業・中小企業の非エンジニアがターゲット
- インストール不要（ZIP解凍 → exe起動）

- UIは日本語のみ

## 起動フロー

1. ZIP解凍 → モノシリ.exe をダブルクリック
1. **初回のみ：セキュリティ確認画面**
   - デジタル署名の発行者情報を表示
   - 「このアプリはインターネットに接続しません（完全ローカルモード）」を明示
1. 初回のみ：Ollamaランタイムの自動検出・インストール
1. 初回のみ：ローカルLLMモデルをダウンロード（進捗バー＋残り時間表示）
   - 表示文言例：「AIが考えるための知識を準備しています（残り約〇分）」
   - ダウンロード失敗時：「ダウンロードに失敗しました。インターネット接続を確認して再試行してください。」
1. フォルダ選択（複数・無制限）
   - 選択後、フォルダ内のファイル数・サイズを表示して確認を促す
1. 前回キャッシュがある場合 → SHA-256差分チェック → 差分のみインデックス更新確認
1. インデックス作成（時間見積もり → 進捗バー → 完了通知）
1. チャット画面へ遷移
   - 初回は**固定の3件**のサンプル質問を表示：「この資料で一番よく出てくるキーワードは？」「生産手順について教えて」「品質基準について説明して」

## インデックス作成

### RAGパイプライン

```
ファイル読み込み
  ↓
テキスト抽出（PyMuPDF / python-docx / python-pptx / openpyxl）
  ※ PDF: 並列抽出（ProcessPoolExecutor）対応
  ↓
チャンク分割（デフォルト1200文字、オーバーラップ500文字）
  ※ RecursiveCharacterTextSplitter使用
  ↓
チェックポイント保存（中断・再開対応）
  ↓
Embedding生成（multilingual-e5-large・ローカル・常時）
  ※ VRAMアダプティブバッチサイズ（GPU搭載時は自動調整）
  ↓
ベクトルDB格納（ChromaDB・ローカル保存）
  ↓
一時ファイル削除
```

### チャンク分割の詳細仕様

- **デフォルト値**: 1200文字（≒600トークン。日本語1トークン≒2文字）
- **分割優先順位**: ①段落末（空行） ②文末（。！？） ③改行 ④文字上限（1200文字）
- **オーバーラップ**: 500文字（前チャンクの末尾をコンテキストとして引き継ぐ。CHUNK-001対応で拡大）
- **最小チャンクサイズ**: 100文字未満のチャンクは前のチャンクに結合する。結合後に1200文字を超える場合は、②文末か③改行での分割を試み、それでも超える場合は④文字上限で強制分割する（**Phase 1実装予定**）
- **Phase 2以降**: MeCab/Janome形態素解析の統合により日本語境界精度を向上

### Producer-Consumerパターン（v4.0追加）

```
Producer（抽出スレッド）:
  ファイルスキャン → テキスト抽出 → チャンク分割 → キューに投入

Consumer（Embeddingスレッド）:
  キューからチャンク取得 → Embedding生成 → ChromaDB格納

制御:
  - キャンセルフラグでの安全停止
  - チェックポイントによる中断・再開
  - IndexManagerシングルトンでバックグラウンド実行管理
```

### チェックポイント機能（v4.0追加: v3.4ではPhase 2）

- チャンク処理の進捗をJSONファイルに記録
- クラッシュ・強制停止後の再開時に、未処理チャンクから継続
- 処理完了ファイル・未完了ファイルの状態を追跡
- インデックス完了時にチェックポイントファイルを自動削除

### バックグラウンドインデックス（v4.0追加: v3.4ではPhase 2）

- IndexManagerシングルトンでバックグラウンドスレッド管理
- インデックス作成中もチャット画面を利用可能
- 進捗・ステータスをリアルタイムでUI反映
- キャンセルボタンでの安全停止対応

### 差分インデックスの詳細仕様

| 状態 | 検知タイミング | 処理内容 |
|------|-------------|--------|
| 新規ファイル追加 | フォルダスキャンでハッシュ管理ファイルに未登録のファイルを検出 | テキスト抽出→チャンク分割→Embedding→DB追加 |
| ファイル変更 | SHA-256ハッシュの不一致を検出 | 旧チャンク削除→テキスト抽出→チャンク分割→Embedding→DB更新 |
| ファイル削除 | ハッシュ管理ファイルに記録あるがフォルダに不在 | 対応チャンク・EmbeddingをDBから削除 |
| 変更なし | SHA-256ハッシュ一致 | 処理スキップ |

> **ハッシュ管理ファイル**: `~/.monoshiri/cache/.hash_manifest`（JSON形式）
> ファイル削除の検知はリアルタイム監視ではなく、**ユーザーが「インデックス更新」を実行した時点**で行う。

### エビデンス表示

|項目        |内容              |
|----------|----------------|
|表示形式     |「フォルダパス ＋ ファイル名」（フルパス）で統一|
|ページ/スライド番号|取得可能な場合のみ表示（PDF・PowerPoint）|

### 該当なし時（v4.0変更: ADR-002）

> **フォールバック回答を廃止し、「正直さ優先設計」に変更。**

類似度閾値以下の場合は以下のメッセージを返す:

```
ご質問に関連する文書が見つかりませんでした。

以下をご確認ください：
・インデックス管理画面で対象フォルダがインデックス済みか確認する
・別のキーワードで質問してみる
```

**変更理由（ADR-002）:** フォールバックがハルシネーション最大の発生源。クラウドAIに切り替えても解決しない設計問題。

### 不十分回答時の外部資料案内（v4.1追加: ADR-002）

類似文書は見つかったがLLMが「資料に記載がありません」等のパターンで回答した場合、回答末尾に以下を自動付加する:

```


---
※ この回答は読み込んでいるファイルを元にしたものです。必要に応じて、外部資料も調査してください。
```

判定対象パターン: `INSUFFICIENT_ANSWER_PATTERNS`（`core/rag.py`）。
LLMがこの注意書き自体をパターン学習しないよう、チャット履歴を構築する際は注意書きを除去してからLLMに渡す（`ui_qt/chat_widget.py`）。

### 類似度設定（v4.1変更: スライダー廃止）

> **v4.1でユーザー向け類似度スライダーを廃止し、開発側で固定値運用に変更。**

- **固定値**: 0.80（`DEFAULT_SIMILARITY`）
- **根拠**: `multilingual-e5-large` の日本語ベクトル分布実測値に基づく最適値。0.40では無関係質問が誤って関連と判定されていた。0.80でUIテストの「全く無関係質問」3問が全て正しく拒否された。
- **廃止理由**: 一般ユーザー（製造業40-60代）にとって閾値調整は意味不明な操作。最適値を開発側で固定して提供する方針に変更。

|項目           |完全ローカルモード        |クラウドAPIモード（Phase 2）|
|-------------|------------------|-----------------|

### セキュリティ実装仕様

#### 1. ベクトルDB（ChromaDB）の保護

- **Phase 1実装済み:**
  - ファイルパーミッション: 所有者のみ読み書き可能（UNIX: 700、Windows: 所有者アクセスのみ）
  - 保存場所: `~/.monoshiri/chroma/`（ユーザー専用領域）
  - ベクトルからの原文復元リスク: multilingual-e5-largeの埋め込みは逆変換困難
- **Phase 2実装予定:** ChromaDBデータのAES-256-GCM暗号化

#### 2. 暗号化・鍵管理（Phase 2）

- APIキー暗号化: AES-256-GCM（IV 96bit・認証タグ 128bit）
- マスターキー管理: Python `keyring`（Windows: DPAPI、macOS: Keychain、Linux: SecretService）
- 初回起動時にランダム256ビットキーを自動生成・保管

#### 3. モデルダウンロードのセキュリティ

- HTTPS強制・証明書検証必須
- ダウンロード元: HuggingFace Hub公式API（ミラーURL設定可能）
- GGUFマジックナンバー検証
- ダウンロードキャンセル時は未完成ファイル削除
- ダウンロードマネージャ: スレッドセーフキュー・自動リトライ（最大3回）

#### 4. 一時ファイル管理

- **Phase 1:** 処理完了・キャンセル・エラー時に削除。チェックポイントは完了時に自動削除
- **Phase 2:** 専用ディレクトリ分離・ゼロ埋め削除・AES暗号化

#### 5. ネットワークセキュリティ

- 完全ローカルモード: アウトバウンド通信なし（Ollama: localhost:11434のみ）
- WebUI: `127.0.0.1:8501`（localhost限定。`0.0.0.0`禁止）

#### 6. アプリケーションセキュリティ

- コード署名: リリースビルドにAuthenticode署名
- 質問テキスト: 最大2,000文字
- プロンプトインジェクション対策: システムプロンプトとユーザー入力を分離
- フォルダパス: パストラバーサル禁止
- 依存ライブラリ: バージョン固定、リリース前CVEスキャン（pip-audit/safety）

#### 7. ログとモニタリング

- ログ: `~/.monoshiri/logs/monoshiri.log`（10MB・3世代ローテーション）
- ログ禁止事項: チャンクテキスト・質問内容・ファイル内容・フルパスをログに記録しない
- スキップログ: ファイル名のみ

## フェーズ分け

### Phase 1（MVP）— 現在のスコープ

- 完全ローカルモードのみ
- PyQt6 + Ollama HTTP API + ChromaDB（v4.1: Streamlit版を削除）
- フォルダ選択 → 差分インデックス → チャット → エビデンス表示
- 5種プリセットモデル（追加・切り替え・削除）
- チェックポイント・バックグラウンドインデックス・プリウォーム
- 正直さ優先設計（フォールバック廃止）
- Free層制限（500ファイル・300質問/月）
- 最小チャンクマージ（**実装予定**）

### Phase 2（個人利用強化 + セキュリティ強化）

- クラウドAPIモード（Gemini Flash / Claude Haiku / GPT-5 Nano）
- AES-256-GCM暗号化（DB・ハッシュ・一時ファイル・APIキー）
- keyringによる鍵管理
- ゼロ埋めセキュア削除
- MeCab形態素解析・Reranker導入検討
- PyInstaller → Nuitka移行
- PCスリープ復帰対応

### Phase 3（集団利用対応）

- インデックス共有・ロック機構・チャットログ共有
- マルチユーザーアクセス制御
- 数百万件規模時のFAISS移行検討

### Phase 4（拡張）

- OAuth2ログイン・多言語化・業界特化テンプレート
