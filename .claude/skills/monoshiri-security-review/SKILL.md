# モノシリ セキュリティレビュースキル

## 概要

「モノシリ」は完全ローカル動作をデフォルトとするRAGデスクトップアプリであり、「社内資料は、一切外に出ません」がコアの価値提案。このスキルは、その設計思想に沿ったセキュリティレビューを体系的に実施するためのもの。

## モノシリのセキュリティアーキテクチャ（前提知識）

### 技術アーキテクチャ原則
1. モデルゼロ書き換え原則：ファインチューニング・再学習は行わない
2. ローカルファースト原則：デフォルトは外部通信ゼロ。クラウドは明示的オプト・インのみ
3. Embeddingは常にローカル原則：モードに関わらずEmbeddingは常にPC内処理
4. 透明性原則：すべての回答にエビデンスを付与
5. ポータブル原則：ZIP解凍→exe起動のみ
6. BYOK原則：クラウドAPIキーはユーザー管理

### 2つの動作モード
- **完全ローカルモード（デフォルト）**: 外部通信ゼロ、APIキー不要
- **クラウドAPIモード（オプション）**: チャンクテキストのみ外部送信、BYOK方式

### 主要技術スタック
- パッケージング: PyInstaller/Nuitka → 単一exe
- UI: Streamlit or FastAPI + ローカルWebUI
- Embedding: intfloat/multilingual-e5-large（ローカル）
- ローカルLLM: llama.cpp + Qwen2.5-7B/3B
- ベクトルDB: FAISS or ChromaDB
- 暗号化: AES-256（APIキー保存時）
- 変更検知: SHA-256

## セキュリティレビュー チェックリスト

レビュー時は以下の7カテゴリを順に確認する。各項目について「対応済み/未対応/一部対応/該当なし」を判定し、未対応・一部対応には具体的な改善提案を付ける。

### カテゴリ1: データ保護とプライバシー

モノシリの最大の差別化要素は「データが外部に出ない」こと。ここが崩れると製品の存在意義が失われる。

- [ ] 完全ローカルモードで外部通信が本当にゼロであることを検証する方法があるか
  - ネットワークモニタリング（例: Wireshark、netstat）での確認手段
  - ファイアウォールルールによるブロック機能の有無
- [ ] クラウドAPIモード時、送信されるデータが「チャンクテキストのみ」であることを保証する仕組みがあるか
  - メタデータ（ファイルパス、ユーザー情報等）の意図しない送信がないか
- [ ] ベクトルDB（FAISS/ChromaDB）のデータが平文で保存されていないか
  - ベクトルからの原文復元リスクの評価
  - DBファイルへのアクセス制御
- [ ] チャンク分割時に、機密情報が不適切に分断・結合されるリスクはないか
- [ ] インデックス作成時の一時ファイルが安全に削除されるか
- [ ] SHA-256ハッシュファイルに機密パス情報が含まれる場合の保護
- [ ] チャット履歴の保存場所と保護方式

### カテゴリ2: 暗号化とキー管理

- [ ] AES-256暗号化の実装が正しいか（暗号モード、IV/Nonce管理、パディング方式）
- [ ] 暗号鍵の生成・保存・ローテーション方式は適切か
  - マスターキーの導出方法（PBKDF2/Argon2等のKDF使用有無）
  - キーがハードコードされていないか
- [ ] APIキー（BYOK）の保存が安全か
  - メモリ上での平文保持時間の最小化
  - 使用後のメモリクリア
- [ ] APIキーが設定ファイルやログに平文で記録されていないか

### カテゴリ3: ネットワークセキュリティ

- [ ] 完全ローカルモードでの外部通信遮断の実装方式
- [ ] クラウドAPIモードでのTLS/SSL通信の強制
  - 証明書検証の有無（証明書ピンニングの検討）
- [ ] HuggingFaceモデルダウンロード時のセキュリティ
  - ダウンロード元の検証
  - ダウンロードファイルの整合性検証（チェックサム）
- [ ] 初回起動時のモデル自動ダウンロードにおけるMITM攻撃リスク
- [ ] ローカルWebUI（Streamlit/FastAPI）のバインドアドレス
  - localhostのみにバインドされているか（0.0.0.0バインドは危険）
  - CORS設定の確認

### カテゴリ4: アプリケーションセキュリティ

- [ ] PyInstaller/Nuitkaでの実行ファイル署名
  - コード署名証明書の使用
  - 改ざん検知の仕組み
- [ ] 依存ライブラリの脆弱性管理
  - 既知のCVEがないか定期チェック
  - サプライチェーン攻撃への対策
- [ ] ユーザー入力（質問テキスト）のサニタイゼーション
  - プロンプトインジェクション対策
  - パストラバーサル攻撃への対策（フォルダ選択時）
- [ ] ローカルLLM（llama.cpp）のバッファオーバーフロー等の脆弱性
- [ ] GGUFモデルファイルの安全性検証（悪意のあるモデルの検出）
- [ ] エラーメッセージによる情報漏洩（スタックトレース、内部パスの露出）

### カテゴリ5: アクセス制御と認可

- [ ] アプリケーションの実行権限（管理者権限不要であるべき）
- [ ] フォルダアクセス権限の最小化（ユーザーが選択したフォルダのみ）
- [ ] Phase 3の集団利用時のアクセス制御設計
  - 共有インデックスへの認可
  - チャットログの閲覧権限
- [ ] Phase 4のログイン機能のセキュリティ設計

### カテゴリ6: ログとモニタリング

- [ ] セキュリティイベントのログ記録
  - モード切り替え、APIキー設定変更、フォルダ追加/削除
- [ ] ログへの機密情報混入防止
  - チャンクテキスト、質問内容、ファイルパスのマスキング
- [ ] スキップログに機密情報が含まれないか

### カテゴリ7: フェーズ別リスク評価

各Phaseで新たに発生するセキュリティリスクを評価する。

**Phase 1（MVP）のリスク:**
- 完全ローカルのみなので外部通信リスクは低い
- 主なリスク: ベクトルDB保護、一時ファイル管理、モデルDL時のセキュリティ

**Phase 2（クラウドAPI追加）のリスク:**
- チャンク送信に伴うデータ漏洩リスクが新規発生
- APIキー管理のリスク
- バックグラウンド処理中のセキュリティ

**Phase 3（集団利用）のリスク:**
- 共有フォルダ経由のインデックス共有における認可
- マルチユーザー環境でのデータ分離
- ロック機構の安全性

**Phase 4（拡張）のリスク:**
- 認証機能のセキュリティ
- 多言語化に伴う入力バリデーションの拡大

## コードレビュー時の追加観点

仕様書だけでなくコードをレビューする場合は、以下も確認する：

- secrets/credentials がコミットに含まれていないか（.gitignore確認）
- ハードコードされた暗号鍵・パスワード・API URLがないか
- デバッグ用のバックドアや緩い設定が残っていないか
- 依存パッケージのバージョン固定（requirements.txt / pyproject.toml）
- セキュリティヘッダー（CSP, X-Frame-Options等）の設定（WebUI部分）
