# ADR-002: ハルシネーション抑制と推論速度改善のアーキテクチャ戦略

**Status:** Proposed
**Date:** 2026-04-09
**Deciders:** Motoki（開発者）

---

## Context

現在の症状は2つ。

1. **ハルシネーション（嘘の回答）が継続発生している**
2. **回答生成が遅い**

「クラウドAIにすれば解決するが、ローカル専用というセキュリティメリットが失われる。
NotebookLMでいいのでは？」という根本的な疑問が浮上している。

本ADRでは、コードベースと設定値の精査から得られた根本原因を示したうえで、
製品仕様レベルで見直すべき事項を整理する。

---

## 根本原因分析

### ① ハルシネーションの原因（3層構造）

#### 第1層：フォールバック設計（最大の原因）

```python
# core/rag.py  answer_question() / stream_question()
if not found:
    fallback_items = search_similar(
        query=question,
        top_k=5,
        similarity_threshold=0.0,  # ← 閾値なし = 何でも取ってくる
    )
```

**問題の本質：** 関連文書がゼロの質問に対しても、最も「近い」チャンクを強引に渡してLLMに回答させている。
LLMはコンテキストを与えられると「それっぽい回答」を作ろうとするため、ここが最大のハルシネーション発生源。

NotebookLMがこの問題を回避できているのは、クラウドモデルの指示追従能力が高いからではなく、
「文書外の質問を拒否するロジック」が適切に実装されているから。
**クラウドに切り替えても、このフォールバック設計を直さない限り嘘は出続ける。**

#### 第2層：TOP_K・閾値の設定が緩い

```python
# core/config.py
DEFAULT_SIMILARITY = 0.35   # ← かなり緩い
TOP_K = 30                  # ← 多すぎる
RAG_CONTEXT_MAX_LENGTH = 6000  # ← 文字数でカット = 後半チャンクが欠落
```

TOP_K=30 × 閾値0.35 という設定では、「多少関係ありそうな」チャンクが大量にコンテキストへ流入する。
ノイズが多いコンテキストはLLMを混乱させ、文書に書いていない内容を「補完」させてしまう。

#### 第3層：量子化モデルの指示追従限界

Q4_K_M量子化（4bit）は元モデルの約50〜60%の精度しかない。
「文書に書いていないことは答えるな」という指示を、量子化モデルは確実に守れない。
これはクラウドAIとの本質的な差であり、ローカルモデルの宿命的な制約である。

---

### ② 速度の原因（2層構造）

#### 第1層：MAX_TOKENSの過大設定

```python
# core/config.py
LLM_MAX_TOKENS = 4096  # BUG-006対応で増やしたが...
```

BUG-006修正でQwen3.5のthinking mode対策として4096に増やしたが、
**Qwen2.5-7B（標準・推奨）にはこれが不要かつ有害**。
Ollama/llama.cppはmax_tokensに比例してバッファを確保するため、
Qwen2.5で4096を指定すると無駄に長い回答を生成しようとする。

Qwen2.5-7Bの社内文書RAGに必要な回答長は概ね300〜800トークン。
1024で十分なところを4096まで待っている状態。

#### 第2層：TOP_K=30のチャンク量

ベクトル検索でTOP_K=30件取得し、6000文字でコンテキストを組み立てる。
これをLLMに渡すと、7Bモデルのアテンション計算量が増大する。
TOP_K=10〜15に絞ればプロンプト長が半減し、推論速度が改善する。

---

## Decision（推奨アーキテクチャ）

**完全ローカルを維持しつつ、「正直さ優先設計」に切り替える。**

クラウドAIに移行しないことを推奨する。根拠は以下の通り：

- 製造業の社内資料には機密情報が多く、外部送信リスクは実際のビジネスリスクになる
- ハルシネーションと速度の問題は、**設計と設定の修正で大幅に改善できる**
- NotebookLMとの差別化は「ローカル専用」という点にあり、この価値を捨てると製品の存在意義が失われる

ただし、Phase 2以降で「セキュリティレベル選択式ハイブリッドモード」を仕様に追加することは合理的。

---

## Options Considered

### Option A: フォールバック廃止 + パラメータ最適化（推奨）

| Dimension | Assessment |
|-----------|------------|
| ハルシネーション抑制 | High — フォールバックを廃止し「わかりません」で返す |
| 速度改善 | High — MAX_TOKENS・TOP_K削減 |
| セキュリティ | 変化なし（完全ローカル維持） |
| 実装コスト | Low — 設定値変更 + rag.py数行修正 |

**変更内容：**

```python
# ① フォールバックの廃止（core/rag.py）
if not found:
    return {
        "answer": (
            "ご質問に関連する文書が見つかりませんでした。\n\n"
            "インデックスされた文書の範囲外の質問か、"
            "類似度が低すぎる可能性があります。\n"
            "・インデックス管理で対象フォルダを追加してください\n"
            "・類似度閾値を下げてみてください（設定画面）"
        ),
        "evidence": [],
        "found": False,
    }
# fallback_itemsブロックを丸ごと削除

# ② MAX_TOKENSをモデル別に設定（core/config.py）
LLM_MODEL_MAX_TOKENS: dict[str, int] = {
    "Qwen2.5-7B-Instruct Q4_K_M（標準・推奨）": 1024,
    "Qwen2.5-3B-Instruct Q4_K_M（軽量）": 512,
    "Qwen3.5-9B Q4_K_M（高性能・最新）": 4096,   # thinking modeあり
    "Nemotron-Nano-9B-v2-Japanese Q4_K_M（日本語特化）": 1024,
}
LLM_MAX_TOKENS = 1024  # デフォルト（後方互換）

# ③ TOP_K削減（core/config.py）
TOP_K = 15   # 30 → 15（ノイズ削減）
DEFAULT_SIMILARITY = 0.40  # 0.35 → 0.40（品質向上）
```

**Pros:**
- ハルシネーション大幅削減（フォールバック廃止が効く）
- 速度30〜50%改善（MAX_TOKENS・TOP_K削減）
- コード変更量が少ない
- セキュリティメリット完全維持

**Cons:**
- 「関連ありそうな参考情報」機能が失われる
- 閾値外の質問への対応が「わかりません」のみになる

---

### Option B: Rerankerの追加導入

| Dimension | Assessment |
|-----------|------------|
| ハルシネーション抑制 | Very High — 高品質チャンクのみLLMに渡す |
| 速度改善 | Medium — Reranker処理分だけ増加する可能性 |
| セキュリティ | 変化なし（完全ローカル維持） |
| 実装コスト | Medium — 新モデルのダウンロード・統合 |

**概要：**
BGE-Reranker-v2-m3（ローカル動作、350MB）を導入し、
TOP_K=30で取得後にRerankerで上位5件に絞り込んでからLLMに渡す。

```
検索（TOP_K=30）→ Reranker（上位5件に絞る）→ LLM
```

**Pros:** チャンク品質が劇的に向上し、ハルシネーションが更に減る
**Cons:** 初回起動時に350MBのモデル追加ダウンロード、RAM消費増、速度はやや落ちる可能性

---

### Option C: クラウドAPIハイブリッド（Phase 2以降）

| Dimension | Assessment |
|-----------|------------|
| ハルシネーション抑制 | Very High — GPT-4o/Claude等の高品質モデル |
| 速度改善 | Very High — サーバーサイドGPU |
| セキュリティ | 低下 — データが外部サーバーに送信される |
| 実装コスト | Medium — APIキー管理、通信設計 |

**Pros:** 品質・速度ともに大幅改善
**Cons:** 「社内資料は一切外に出ません」という最大の価値提案が崩れる

**Phase 1での採用は推奨しない。** ただし以下の設計を検討すると合理的：
- 「セキュリティレベル選択」UI：High（完全ローカル）/ Standard（クラウドAPI）
- APIキーは完全にユーザー管理（モノシリのサーバーは経由しない）
- ローカルモードが「デフォルト」
- これはPhase 2（有料プラン）の機能として検討

---

## Trade-off Analysis

| 観点 | Option A（推奨） | Option B（+Reranker） | Option C（クラウド） |
|------|--------------|-----------------|----------------|
| ハルシネーション | 大幅改善 | 最良 | 最良 |
| 速度 | 大幅改善 | 同程度 | 最速 |
| セキュリティ | 完全維持 | 完全維持 | 低下 |
| 実装コスト | 低 | 中 | 中 |
| Phase 1採用 | ✅ 推奨 | ✅ 後続実装として | ❌ 非推奨 |

**結論：**
まずOption Aを即実施する（設定変更のみ）。
Option BのRerankerはPhase 1後半の品質強化施策として検討する。
Option CはPhase 2の差別化機能として仕様に追加する。

---

## Consequences

### 容易になること
- 「この質問には答えられない」という正直な回答の信頼性向上
- ユーザーがインデックスの充実度を意識するようになる（健全な使い方の促進）
- 回答生成速度の体感改善（Qwen2.5で30〜50%速くなる見込み）

### 困難になること
- 「フォールバックで何か見つかる」という現在の挙動に慣れたユーザーの違和感
- 「わかりません率」が増えるため、インデックスの品質管理がより重要になる

### 今後見直しが必要なこと
- **stream_question()** にも同様のフォールバック廃止を適用すること
- **Phase 2のクラウドハイブリッドモード**：APIキー管理・プライバシーポリシー・料金体系の設計
- **Reranker導入**：BGE-Reranker-v2-m3の評価・統合
- **信頼度スコアのUI表示**：evidence の similarity 値に基づく警告表示
- `LLM_MODEL_MAX_TOKENS` 設定をUI（設定画面）から調整できるようにする
